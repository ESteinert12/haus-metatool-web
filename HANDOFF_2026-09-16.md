## 1. Verification still needed: mix_stems collision check

**Why:** `detectStemName()` in `index.html` previously collapsed every lettered
`BUMPER`/`ALT` variant into the bare stem name — `BUMPERa`, `BUMPERb`, `BUMPERc`
all became `'BUMPER'`; same for `ALT`. Fixed today (see §3), but the fix is
forward-only. If any composer already delivered lettered BUMPER/ALT variants
before today, those files may have collided in `mix_stems` — either overwritten
each other on insert, or sitting there as duplicate/ambiguous rows under the
same `stem_name`.

**Run this once `DATABASE_URL` is reachable** (it wasn't from the session that
did this work — no local `.env` value and no way to reach Neon from the cloud
sandbox):

```sql
-- Multiple rows for the same sku_root + stem_name is the collision signature
-- this bug would produce.
SELECT sku_root, stem_name, COUNT(*) AS n
FROM mix_stems
WHERE stem_name IN ('BUMPER', 'ALT')
GROUP BY sku_root, stem_name
HAVING COUNT(*) > 1
ORDER BY n DESC;

-- Cross-check against what's on disk: filenames literally containing
-- BUMPERA/BUMPERB/BUMPERC/ALTA/ALTB/ALTC that got tagged as the bare name.
SELECT sku_root, stem_name, filename
FROM mix_stems
WHERE stem_name IN ('BUMPER', 'ALT')
  AND filename ~* '(BUMPER|ALT)[ABC]\.'
ORDER BY sku_root;
```

If either query returns rows, those tracks need manual review — the DB row's
`stem_name` won't tell you which physical file (base, a, b, or c) it actually
points to anymore. Not something to auto-fix without eyes on the data.

## 3. detectStemName() fix (index.html)

`ALT`/`BUMPER`/`STING` now each preserve up to 4 variants (base, a, b, c) instead
of collapsing lettered variants into the bare name. Verified with 21 hand-built
test cases run against the actual function (not just a syntax check), including
a false-positive guard case (`StingRay` in a title doesn't get misread as a
STING stem). See §1 above for the retroactive-data question this doesn't answer.
