## THE BIG MISUNDERSTANDING, SETTLED WITH MEASUREMENT
For two days the HEARTLAND lot looked like it held 13-16 songs while the app
showed 9. It did not. Intake NEVER renames the composer's folder: it creates a
new `{SKU}_{Title}` folder, copies each file in under its HAUS name, and leaves
the original alone. Commit 1acc119 (Sep 3 16:58) started dropping that original
INTO the lot folder, so the folder ran at ~2 entries per song and the unrenamed
ones read as "the naming failed".
Proof, not opinion: every audio file in all 7 `_SOURCE` folders was matched
byte-for-byte to a file already in one of the 9 song folders. No `_SOURCE`
folder held a song that was not already in the lot. Processing them would have
minted 7 duplicate SKUs.
**Lesson: count only `{sku_root}_...` folders, and compare by content, not name.**

## WHAT CHANGED (all reviewed by Erik, in his words where quoted)
1. **Old lots are OUT OF SCOPE.** 1,727 of 1,737 lots have no project_id. "I
   don't care about old Lots... only concerned with moving forward." Do not
   propose backfilling them again.
2. **Reverted to Sep 2 behaviour**, then improved past it. ATMOS_Finish is NOT
   an archive -- it is the legacy two-stage FileMaker/SourceAudio backlog. In
   ATMOSPHERE a song is FINISHED at intake, so the original folder has no
   reason to exist ("mindnumbingly confusing"). Intake now touches cfg.finish
   nowhere. The normal path RETIRES the source folder; the duplicate-SKU path
   always keeps it for human comparison.
3. **The source is deleted ONLY with two verified copies**: byte-matched in
   Shipping AND every file carrying a confirmed B2 key. Any gap, or B2 not
   connected, and the folder stays and is reported. Deletion is file-by-file
   `rm` then `rmdir` -- never `rm -r`, which the shell/exec guard refuses by
   design, and rmdir refusing on unexpected content is the wanted behaviour.
4. **B2 disconnected now asks once** at the start of a run instead of warning
   only in the console.
5. **VOCALS BUG (real).** The intake form collected vocals but executeIntake
   never passed it to writeTrackToDB, so EVERY song ever logged saved as
   'no_vocals'. Found by Erik comparing the form (Female Vocals) with the edit
   modal (No Vocals). Fixed; R48a5904 corrected by hand. Earlier songs hold a
   possibly-wrong value and the real choice was never stored anywhere -- only
   ears can recover it. Erik is fixing those himself.
6. **AVID export path (real bug).** /api/lot/download-avid-wavs read only
   HAUS_SHIPPING / ~/.haus-workspace-cfg.json -- still pointing into Dropbox
   CloudStorage -- while the app had moved to ~/Downloads. Two sources of
   truth. The client now sends `shippingBase: cfg.hausjup` and the server
   prefers it; the not-found error now names the path searched and lists the
   folders actually there. **api.js changed -> needs a server restart.**
   Kyle's USER_PATH_DEFAULTS shipping path also pointed at Dropbox; now the
   same local folder for everyone. "It all needs to come from the same place."
7. **The AVID export walks the lot folder RECURSIVELY** and copies every .wav
   flat. So anything nested in a lot folder gets exported too. Keep lot folders
   SKU-folders-only. (This is why `_SOURCE` had to come out before exporting.)
8. **Lot pickers now share one rule: ACTIVE lots, newest first, 50 max** --
   not sent, not closed, not at their track limit, each row showing its fill
   (`16/30`). The intake picker had been filtering on the client columns and
   showed only ONE lot, because the show name lives in `client` on some lots
   and the production company on others. The Add/Move list in the metadata
   editor was showing all 200 by name. Erik: "perfect logic".
9. **Add vs Move is now explicit.** Both behaviours existed but were invisible
   (header button added, row arrow moved) and either committed on the spot. A
   song legitimately belongs to several lots -- the same track sent to a second
   client -- so the user is asked: Add (keep the other lots, move no files) or
   Move (leave a named lot and take the files). A move now also updates
   titles.lot_id, which it never did.
10. **Clicking a song in a Clients lot list opens the metadata editor**, same
    as in Lots.
11. **The `.5` and `2x` BPM buttons are back** beside TAP (detection lands on
    an octave: 180 for 90, 65 for 126). NOT a restore -- no copy survived in
    either checkout's history or any backup. Rebuilt.
12. **New Lot modal**: confirm screen shows the Project; Back keeps client,
    project, name, limit and intake context; client preselect is
    case-insensitive. Rollover popup rebuilt with Client + Project.

## LATE IN THE DAY: THE SILENT-SAVE GLITCH (unresolved cause, guarded)
Symptom Erik reported: a song processes fully -- SKU issued, files renamed into
Shipping, exports fine in the AVID WAV set -- but stays in Intake, shows no
metadata, and is missing from the AVID Comments CSV.

Found by diffing the Desert 2 lot folder against `titles`: TWO songs had SKU
folders and NO DATABASE ROW AT ALL (no titles, no mix_stems, no lot_titles, no
.md log):
- **S33a49594 In The Sand Country** -- and its STAGING FOLDER WAS GONE.
- **S33a49654 Left The Road** -- staging folder intact, which is why it kept
  showing in Intake.
They sit minutes apart between successful songs, same composer, no title clash,
nothing odd about the files. The AVID WAV export listed them because it reads
the FOLDER; the comments CSV did not because it reads the DATABASE. Cause of
the failed INSERT is UNKNOWN -- most likely an intermittent /api/pg/query
failure. **The console line `[writeTrackToDB] INSERT returned nothing for
sku_root ...` is what will identify it.** Get that next time it happens.

MY BUG, fixed: the source-retirement check required a byte-matched Shipping copy
and confirmed B2 keys but NOT a successful DB write, so a failed save could and
did delete the composer's original. It now also requires `dbResult?.skuRoot`
and reports "the song was NOT saved to the database". Backup
index.html.bak-dbguard-*.

Recovery done:

  (nothing deleted), re-run through intake, now **S33a49724**, saved clean.
- In The Sand Country: staging gone, so it could not be re-run. Rows created by
  hand from the files -- titles (lot 7619, S33a, TM1372, key Asharpm) + 6
